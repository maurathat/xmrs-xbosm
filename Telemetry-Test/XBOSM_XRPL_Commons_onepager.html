We tested a simple question against live mainnet telemetry: if XRPL nodes forwarded each transaction to a fixed handful of peers instead of flooding all of them, how much relay bandwidth is saved — and how much message reachability is lost?

What we did

Captured 45 minutes of live XRPL ledger telemetry from public servers — 427 ledgers, 39,474 transactions, mean 92 tx/ledger, peak 556. One row per closed ledger using each ledger's authoritative transaction count.

Ran a Monte-Carlo gossip simulation on a 200-node peer graph, comparing flood against selective-k forwarding (each node relays to k random peers). Bandwidth is measured as relay events; reachability as the fraction of nodes that receive a message.

Why it's credible

Every parameter is sourced, not assumed. Peer degree is set to rippled's documented default soft-max of 21. The headline uses sender-suppressed gossip — the realistic model every protocol implements — not the flattering dedup-free upper bound.

We report a bracket, not a single number: 67% under realistic suppression, 39% as a conservative floor. The result travels with its peer-degree assumption and a full sensitivity sweep.

Selective forwarding is self-limiting: k8's relay count stays near-flat (~1,360–1,540) as the graph densifies, while flood scales linearly. The denser the network, the larger the saving.

What we'd value from XRPL Commons

  • Ground-truth peer counts. Our degree-21 anchor is the documented default — real distributions from operators would tighten the headline.
  • A longer, richer capture. 45 min caught 6 single-ledger spikes and no sustained congestion episode; a multi-hour run would strengthen the detection claim.
  • Relay-layer reality-check. Does rippled's transaction relay behave closer to our sender-suppressed model or the peer-aware floor?
  • Operators to test with. Anyone running a node who'd compare simulated vs. observed relay load.
